# Isolation Sphere — soloモード実装ハンドオフ

## 目的と実装依頼

既存のserver＋core構成を維持しつつ、外部serverなしで球体単独再生できる`solo`モードを追加してください。この文書を基に、現行コード調査、実装、ビルド・検証、利用手順の更新まで進めてください。

対象リポジトリ: https://github.com/sastles-com/sastle-isolation-sphere

この文書の作成時にはリポジトリへのアクセスが404となり、最新コードを読めていません。実在するファイル名・API・タスク配置は未確認です。以下の設計案を既存実装の事実として扱わず、必ず現行コードとAGENTS.mdを確認してください。既存の設計・命名・ビルド方式を尊重し、無関係な変更は避けてください。

## ユーザーが指定した条件

| 項目 | 条件 |
| --- | --- |
| デバイス | ESP32-S3、PSRAM 8MB、flash 8MB |
| 現行構成 | server＋core。UIと動画配信はserver側へ移動済み |
| 新モード | solo。外部serverなしで動作 |
| 操作端末 | iPhoneがメイン |
| 通信 | Wi-Fiベース。Bluetoothは今回採用しない |
| 動画 | 320×160を前提に検討、10fps固定、音声なし |
| 保存・起動 | LittleFSへ動画をアップロードし、起動するとそれを再生 |
| コンテンツ | アップロードした1本だけを再生。プレイリスト・動画一覧は不要 |
| フロントエンド | 現行UIと同一でなくてよい。必要最低限 |
| 互換性 | 既存server＋core構成と設定で切り替えられるよう検討・実装 |

MQTTによるUIコマンド受信と動画受信用UDPは既存モードに残し、soloでは起動しない。内部制御のためにMQTTブローカーを追加しない。「UDP不要」は動画受信用UDPの意味であり、Wi-Fi接続に必要なDHCPなどまで無効にしない。

## 今回の実装に用いる暫定方針

以下は会話中の提案を実装可能な初期仕様にまとめたものです。現行コードを調べて合理的な調整が必要なら、理由を記録してください。

- ESP32-S3のSoftAPへiPhoneを直接接続し、SafariでローカルWeb UIを開く。外部ルーター・インターネットを必須にしない。
- UIのHTML/CSS/JSをデバイス内に配置。CDNや外部フォントなどに依存しない。
- 再生ファイルは320×160のBaseline JPEGを連続格納するMJPEGを第一候補とする。既存デコード形式と共用できる場合は優先する。
- 10fpsはファームウェアの固定値。音声、シーク、複数動画管理は実装しない。
- 有効な保存済み動画があれば起動時に自動ループ再生。Wi-Fiクライアント接続を待たない。
- iPhoneの切断後も再生を継続。
- アップロード中は再生を停止。成功後は新しい動画を先頭から再生。
- solo／既存モードの切替は設定を永続化して再起動で反映。稼働中の無停止切替は初期版の対象外。
- 初期版では事前変換済みファイルをアップロードする。MP4/MOV/HEVCをESP32上で変換しない。iPhone内の元動画を直接変換するブラウザー機能も対象外。

## 最初に調査すること

1. ビルド環境、SDK・ライブラリのバージョン、ボード定義、PSRAM設定、flash容量・パーティション表、OTAの有無。
2. core側の起動処理、FreeRTOSタスク、CPU affinity、優先度、スタックサイズ、割り込み、LED駆動方式、IMU・姿勢補正周期。
3. 現行serverから送るフレーム形式・解像度・JPEG品質・サイズ、coreのデコーダーと出力画素形式。
4. MQTTコマンド処理とUDP受信から表示までの経路。ネットワークに依存せず共用できる境界。
5. LittleFSと設定保存の既存実装、Webサーバーの有無、既存モードへ戻す操作方法。

現在のコードから判明した事実と、この文書から採用した設計判断を分けて報告してください。認証・アクセス不能の場合はソースを推測して実装せず、必要なアクセスまたはファイルを具体的に示してください。

## 再生・制御アーキテクチャ

| 境界 | 既存モード | soloモード |
| --- | --- | --- |
| 映像入力 | 既存UDP受信 | LittleFSから読み込み |
| 制御入力 | 既存MQTT | ローカルHTTP API（必要ならWebSocket） |
| 表示 | 既存の姿勢補正・LED表示を共用 | 同左 |

概念的に「フレーム供給」と「操作コマンド入力」を差し替え、表示エンジンと制御ロジックを共用してください。抽象化の名前やディレクトリ構成を新規に押し付けず、既存コードに合う最小限の分離としてください。

### タスクと時間管理

- 配置の出発点はCPU Core 0にWi-Fi・操作・ファイル先読み・デコード、CPU Core 1に周期を守りたい姿勢補正・表示処理。ただしこれは未計測の案であり、現行の割り込みやSDKタスクを調べて決定すること。
- 動画更新は100ms周期。デコード完了後に100ms待つ実装ではなく、単調増加時刻を使った締切管理とし、処理時間による累積ドリフトを避ける。
- JPEGのデコードは動画の新フレームごとに行う。姿勢補正・LED更新を10Hzに落とさず、最新の展開済み画像を使い既存の周期を保つ。
- ダブルバッファ等により、描画中のフレームを書き換えない。所有権と交換タイミングを明確にする。
- 期限に間に合わない場合の動作（直前の完全なフレームを維持、必要ならフレームをスキップ）を定義し、遅延の無限蓄積やbusy loopを避ける。
- DMAやISRのメモリ制約を確認し、すべてを安易にPSRAMへ移さない。フラッシュ書き込みの影響は別コアへの配置だけでは解消しない。

### 動画形式

- 受理するファイル形式を1種類に明確化する。raw MJPEG、AVI内のMJPEG、multipart MJPEGを混同せず、選んでいない形式を拒否する。
- raw MJPEGを採用するなら、JPEGの境界・長さ・解像度・形式・破損・途中EOFを適切に検査する。読み込みバッファ境界をまたぐマーカーにも対応する。
- 上限フレームサイズを設け、サイズ値を無検証でメモリ確保に利用しない。
- 320×160、Baseline JPEG、10fps用の事前変換手順または小さな変換スクリプトを提供する。JPEG品質・サブサンプリングは採用デコーダーで検証する。
- fpsは固定値なのでファイル内のfpsメタデータは必須ではない。320×160以外や非対応JPEGは明確なエラーにする。
- 姿勢補正が必要な画像情報を残す。姿勢に依存する最終LED出力列へ事前変換しない。

## 容量とアップロード

flash 8MB全体を動画領域として見積もらない。ファームウェア、既存OTA領域、設定、UI、LittleFSの管理・空き領域を考慮し、実際のパーティション表からアップロード上限を決める。既存OTAを黙って削除しない。パーティション変更で既存データが消える場合は、移行手順に明記する。

展開画像の概算は、RGB565で1枚100KiB／2枚200KiB、RGB888で1枚150KiB／2枚300KiB。これはデコーダー作業領域や通信バッファを含まない。

仮に動画に4MiB使える場合、10fpsでは平均5KiB/枚で約82秒、10KiB/枚で約41秒、20KiB/枚で約20秒。この数字は例であり、実容量・画質の保証ではない。

アップロードはストリーミング書き込みにし、全ファイルをRAMに保持しない。中断・容量不足・不正形式・書き込み失敗を扱い、部分ファイルを有効動画として起動時再生しない。

容量に余裕があれば、一時ファイルに書き込み・検証後に有効ファイルへ切り替える。二重保存が容量を圧迫する場合は、置換開始時に旧動画を削除する方針も選べるが、UIにその動作を明示し、失敗時は「有効動画なし」で再アップロード可能にする。電源断を含めた置換方針と必要な空き容量を文書化する。

## 最小Web UIと操作

- ファイル選択、アップロード開始、進捗表示。
- 状態表示：動画なし／再生中／停止中／アップロード中／エラー。
- 再生・停止、明るさ調整。
- solo／既存モードの設定と、再起動で反映することの表示。
- 選択可能な動画一覧、プレイリスト、サムネイル、動画プレビュー、タイムラインは不要。
- iPhone Safariで操作できるレイアウト。Web Bluetoothや専用アプリは使わない。

HTTP APIだけで十分ならWebSocketを追加しなくてよい。状態取得は低頻度ポーリングでも可。アップロードと再生操作が競合しない状態管理を実装する。

SoftAPのSSID・接続方法・ローカルURLを明示する。名前解決がなくてもIPアドレスでアクセスできるようにする。キャプティブポータルは必須ではない。

## 設定と復帰経路

- 既存設定方式に合わせてモードを永続化。未設定時は原則として従来モードを維持し、既存ユーザーの動作を変えない。
- soloではMQTT接続待ちやserver探索が起動・再生を妨げないようにする。
- 両方向の切替経路を用意する。solo UIから従来モードへ戻せるだけでなく、従来モードからsoloへ入る設定方法も提供する。
- server不在でもsoloへ移行できる復帰方法を最低1つ用意する。既存のシリアル設定、設定ファイル、実在するボタン操作などから選び、存在しないボタンを前提にしない。
- 動画なし・破損時でも管理UIを起動し、再アップロードできるようにする。マウント失敗時に無断で全領域をフォーマットしない。

## 検証と完了条件

ソース／ビルドで検証できたことと、実機で確認したことを明確に分ける。実機がない場合は完了扱いの性能値を作らず、次の実機チェック手順を残す。

- 対象ボード設定でビルドが通る。実行コマンドと結果を報告。
- 正常動画、破損／途中切れ、解像度違い、過大フレーム、容量不足、アップロード中断の扱いを検証。
- 保存動画ありの起動で、serverもiPhoneも不要で自動再生し、EOFでループする。
- LittleFS読み込み＋デコードの時間、フレーム締切超過、空きヒープ／PSRAM、主要タスクのスタック余裕を確認。
- 動画10fpsと姿勢補正・LED更新を独立させ、再生中に回転させても従来の追従性を維持するか実機確認。
- iPhone Safariから接続・アップロード・再生停止・明るさ変更ができ、切断後も再生を継続。
- アップロード失敗や電源断の後、部分ファイルを再生せず復旧操作ができる。
- solo／従来モードを両方向に変更でき、再起動後も設定を保持。
- 従来モードのMQTT操作・UDP動画受信・姿勢補正・LED表示が維持される。

テストはパーサーの境界条件、状態遷移、既存機能への回帰など具体的なリスクに絞る。
